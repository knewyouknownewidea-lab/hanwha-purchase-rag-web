구매관리 RAG 백엔드와 벡터 DB
============================

현재 폴더 구성 (2026-10-26 정리)
------------------------------

원본 업무 DB와 SQL은 db/, 검색 문서·청크·벡터DB는 data/에 있습니다.
평가 질문과 원시 결과는 evaluations/, PDF·HTML·이미지는 reports/에서 찾으세요.
공통 경로는 project_paths.py에서 관리합니다. 프로젝트 루트 README.rst에
전체 구조와 최신 실행 순서를 정리했습니다. 아래 절은 기능이 추가된 순서를
기록하므로, API의 현재 기능은 뒤쪽 버전의 설명까지 함께 확인하세요.

1. 무엇을 만든 건가요?
----------------------
VS Code는 편집기입니다. backend 폴더의 Python 코드를 실행하면 백엔드 서버가 됩니다.
지금 서버는 현재 PC의 가상 데이터 SQLite DB를 사용합니다.
팀원의 Java/Spring 서버나 실제 회사 DB와 아직 연결하지 않았습니다.

저장 흐름 (POST /index):
원본 SQLite DB 읽기 -> backend/documents.py의 ID 연결/문서 생성 -> LangChain 청킹
-> BGE-M3로 1024차원 벡터 생성 -> Chroma에 원문/벡터/출처 ID 저장

검색 흐름 (POST /search):
질문 -> 같은 BGE-M3로 질문 벡터 생성 -> Chroma 검색 -> 근거 문서와 원본 ID 반환
질문할 때마다 모든 문서를 다시 임베딩하지 않습니다.
AI의 최종 답변 생성은 다음 단계입니다. 유사도는 정답 확률이 아닙니다.

2. 파일 역할
------------
db/구매관리_테스트.db: 원본 6개 테이블. 백엔드는 읽기 전용으로 접근합니다.
backend/documents.py: 원본 레코드를 연결해 검색 문서로 바꾸는 기존 코드입니다.
backend/service.py: 문서화, 청킹, 임베딩, 저장, 검색을 실행하는 핵심 로직입니다.
backend/app.py: 브라우저나 Java 서버가 요청할 API 주소를 정의합니다.
backend/__main__.py: 서버 시작 코드입니다.
data/vector_store/chroma/: 디스크에 저장되는 Chroma 데이터입니다.
data/vector_store/active.json: 현재 검색에 사용할 인덱스와 모델 버전을 기록합니다.

원본 DB와 벡터 DB는 별개입니다. 벡터 DB는 검색용 복사본이며 원본을 대체하지 않습니다.
비교 실험의 .npz 파일을 단순 복사한 것이 아니라 백엔드 로직으로 직접 구축합니다.

3. VS Code에서 실행하기
-----------------------
기존 구매관리_RAG.code-workspace를 엽니다.
메뉴 [터미널] -> [작업 실행]에서 아래 작업을 선택합니다.

  1) 백엔드: 서버 시작
  2) 벡터DB: 구축 및 갱신
  3) 벡터DB: 상태 확인
  4) 벡터DB: 예제 검색

서버를 실행한 뒤 브라우저에서 http://127.0.0.1:8000/docs 를 엽니다.
POST /search를 펼치고 [Try it out]을 누른 다음 아래 JSON을 입력하고 [Execute]합니다.

  {"question": "베어링 완충 포장이 부족하다는 민원을 찾아줘", "top_k": 3}

정확한 발주 번호를 알고 있으면 order_id 필터를 함께 지정할 수 있습니다.
현재 질문의 ID·날짜·조건 처리는 아래 v1.1 설명을 참고하세요.

  {"question": "누적 납품 수량과 남은 수량은?", "top_k": 3,
   "order_id": 1101, "document_type": "order"}

GET /status의 count는 저장된 청크 수입니다.
source_changed가 true이면 원본 DB가 변경되었으므로 POST /index를 다시 실행하세요.
데이터가 같으면 unchanged를 반환하고 중복 저장하거나 재임베딩하지 않습니다.
삭제된 원본 문서는 다음 구축 후 활성 인덱스에서도 제외됩니다.
갱신 실패 시 이전 인덱스를 유지합니다. 이전 인덱스는 복구를 위해 디스크에 남습니다.

4. 실행 환경과 재설치
---------------------
현재 VS Code 작업은 프로젝트 옆 work/chunking-venv의 Python을 사용합니다.
requirements.txt는 Python 패키지 설치 목록입니다. 사용 설명 TXT 파일과는 다릅니다.
새 PC에서는 Python 3.12 가상환경에 이 목록을 설치한 뒤 outputs 폴더에서 실행합니다.

  python -m pip install -r backend/requirements.txt
  python -m backend

모델은 처음 사용할 때 다운로드되며, 현재 PC에는 이미 다운로드되어 있습니다.
모델 캐시는 work/huggingface에 있습니다. API 키나 유료 API를 사용하지 않습니다.
서버 종료 후에도 벡터 DB는 남습니다. 서버를 다시 시작하면 같은 경로에서 읽습니다.
VS Code 작업으로 시작한 서버는 백그라운드에서 계속 실행됩니다.
중지하려면 [터미널] -> [작업 실행] -> [백엔드: 서버 중지]를 선택하세요.
직접 python -m backend로 시작했다면 해당 터미널에서 Ctrl+C로 중지합니다.
로컬 테스트용으로 127.0.0.1:8000만 사용하며 한 프로세스로 실행합니다.
다른 사람에게 공개하는 서버 배포/인증과 여러 프로세스 운영은 아직 구성하지 않았습니다.

5. 팀원의 Java 백엔드와 연결할 때
--------------------------------
Java/Spring 서버가 이 Python 서버의 POST /search를 HTTP로 호출할 수 있습니다.
Python은 BGE-M3/벡터 검색을 담당하고 Java는 기존 업무 API를 유지할 수 있습니다.
실제 DB 연동 시 SQLite 조회 부분을 실제 DB 조회 또는 Java 데이터 API로 교체해야 합니다.
현재 Java 엔티티 파일만으로 실제 DB에 자동 연결되지는 않습니다.

6. 확인한 설정
--------------
LangChain RecursiveCharacterTextSplitter: 800자, 겹침 0자
BGE-M3: 1024차원, 정규화한 밀집 벡터, CPU 실행
Chroma: 코사인 거리, 원문과 원본 ID를 함께 저장
현재 47개 문서는 모두 800자보다 짧아 문서 1개가 청크 1개입니다.
source 출처는 부모 문서 전체 범위이며 청크의 모든 문장과 1:1 대응한다는 뜻은 아닙니다.


7. 유사도 필터와 근거 부족 처리
------------------------------
similarity_policy.json의 min_similarity(현재 0.619865) 이상인 문서만 반환합니다.
결과가 없으면 evidence_status는 insufficient_evidence, message는 근거 부족,
results는 빈 배열입니다. 통과하면 candidates_found이며 정답을 보장하지 않습니다.
후속 답변 생성에서는 insufficient_evidence일 때 답변 생성을 건너뛰고 근거 부족을 표시하세요.
통과한 후보도 실제로 질문의 답을 포함하는지 별도 검토가 필요합니다.
기존 예제 질문도 점수가 낮으면 이제 근거 부족으로 반환될 수 있습니다.

평가: 정답 있는 30문항 + 없는 30문항을 먼저 고정하고 각 종류를 15/15로 나눴습니다.
기준 선택 30문항과 검증용 30문항은 분리했습니다. 문서 단위 분리는 아닙니다.
검증용 정답 질문: 11/15 근거 유지, 4/15 거절.
검증용 정답 없는 질문: 12/15 거절, 3/15 잘못 통과.
따라서 이 기준은 현재 가상 데이터용 잠정 기준이며 완전한 무응답 판별기가 아닙니다.
평가는 필터 없이 top_k=3으로 수행했습니다. ID 필터 사용/다른 top_k는 같은 성능을 보장하지 않습니다.
calibration_matches_index가 false이면 데이터/인덱스가 달라졌으므로 재평가해야 합니다.

evaluations/datasets/유사도_평가셋.json: 질문과 정답 유무, 분할 기록
evaluations/results/backend/유사도_검증결과.json: 원래 후보 점수, 기준 선택, 보류 평가, 실제 API 재검증 결과
backend/calibrate_threshold.py: 저장된 필터 적용 전 결과로 기준을 재현합니다.
새 데이터 평가 시 필터 적용 전 후보를 별도로 수집해야 합니다. 필터 적용된 결과로 재학습하지 않습니다.


8. 조건 검증 및 정확 조회 추가 (v1.1)
------------------------------------
/search는 이제 query_rules.py로 질문을 먼저 분석합니다.
정확한 발주 ID/저장 점수/등록 단가 조회는 원본 DB를 읽어 조건을 검증합니다.
retrieval_method=structured_db, embedding_used=false, similarity=null로 반환합니다.
이 경로에는 기존 유사도 기준을 적용하지 않습니다. 낮은 의미 유사도로 정확 조회를 거절하지 않기 위함입니다.
민원 내용 검색은 조건에 맞는 문서만 Chroma에서 검색하고 기존 0.619865 기준을 유지합니다.
없는 항목/ID/협력사/부품/기간 기록은 insufficient_evidence입니다.
조건 충돌, 연도 없는 날짜, 상대 날짜, 미지원 집계는 clarification_required입니다.
정확 조회에는 상수 점수 1을 만들어 붙이지 않습니다. 근거는 원본 DB의 ID와 내용입니다.
지원 언어는 규칙으로 정의한 한국어 표현이며 범용 자연어 이해를 보장하지 않습니다.
민원 날짜와 납품 날짜가 함께 등장하면 어떤 날짜인지 명시해야 합니다.
단가 비교/집계/기간 납품량 합산은 아직 지원하지 않습니다.

evaluations/조건검증_전후평가.py는 현재 API를 기존60개 개발문항과 추가12개 회귀사례로 확인합니다.
과거 evaluations/sklearn_유사도필터평가.py는 순수 벡터 필터 동작과 같다는 assertion이 있어
현재 라우팅 API에 그대로 실행하면 실패할 수 있습니다. 과거 결과는 변경하지 않고 보존했습니다.
새 평가는 임베딩 모델 자체의 향상이 아닌 DB 조회/조건 검증을 포함한 전체 검색 흐름 개선입니다.


9. 질문과 검색 근거 통합 (v1.2)
--------------------------------
POST /prepare-prompt는 기존 /search 결과를 사용자 PROMPT_TEMPLATE에 채웁니다.
질문, 검색 문서 원문, [E1] 형태의 근거 번호와 원본 DB 출처를 보존합니다.
이 API 자체는 생성 모델을 호출하지 않습니다.


10. Ollama 답변 생성 연결 (v1.3)
--------------------------------
Ollama를 실행한 뒤 http://127.0.0.1:8000/docs 를 엽니다.
GET /models에서 선택 가능한 모델의 설치 여부를 확인할 수 있습니다.
POST /answer를 펼치고 Try it out을 누른 다음 아래 JSON을 입력합니다.
gemma3:4b는 실행 예시이며, 기본 모델은 지정하지 않았습니다.

::

    {
      "question": "발주 1101의 납품 수량과 남은 수량은?",
      "model": "gemma3:4b",
      "top_k": 3
    }

model은 qwen3:8b / gemma3:4b / llama3.1:8b 중 하나를 필수로 선택합니다.
채점용 qwen3:14b는 답변 생성 API의 선택 목록에 넣지 않았습니다.

처리 흐름:
질문 -> 기존 검색 및 조건 검증 -> 프롬프트 구성 -> 로컬 Ollama -> 답변과 사용 출처.

응답의 주요 항목:
answer: 실제 생성 답변 또는 근거 부족/추가 정보 요청 문장.
generation_model: 사용자가 요청한 모델.
model_called: 정상 응답에서는 실제 모델 호출 여부.
연결 실패/시간 초과 오류의 model_called=null은 실행 여부를 확정할 수 없다는 뜻입니다.
sources: 답변에 표시된 근거 번호와 원본 DB의 행 ID.
citation_check=valid_ids_only: 존재하는 출처 번호인지 확인했다는 뜻.
문장별 사실 정확성이나 수치 정확성을 자동 검증했다는 뜻은 아닙니다.

status:
answered: 생성 완료 및 출처 번호 확인.
insufficient_evidence: 근거 부족. 검색 단계에서 판정되면 모델을 호출하지 않음.
clarification_required: 조회 ID/기간 등의 추가 정보 요청. 모델을 호출하지 않음.
context_limit_exceeded: 입력이 길어 모델을 호출하지 않음. 근거를 임의로 자르지 않음.
invalid_generation: 출처 표기가 없거나 없는 근거 번호를 사용하여 답변을 반환하지 않음.

503: Ollama 연결 또는 모델 설치 상태 확인 필요.
504: 응답 시간 초과.
502: Ollama 실행 실패, 빈/불완전 답변, 입력 길이 정보 오류 등.

모델 설정은 generation.py의 OPTIONS에 기록했습니다.
기존 PC에서 확인된 CPU 4스레드, 입력 8192, 출력 1024, temperature 0, seed 42를 사용합니다.
긴 근거는 UTF-8 바이트 수로 보수적으로 제한하므로 허용 가능한 입력도 제한될 수 있습니다.
한 요청씩 생성하고 요청 완료 후 모델을 메모리에서 내리도록 keep_alive=0을 사용합니다.
모델 최초 로딩에는 시간이 걸릴 수 있습니다.

Ragas 채점 재개와 최종 모델 선정은 별도 작업입니다.
이번 연결은 모델을 선택해서 실제 응답을 생성하는 기능입니다.
